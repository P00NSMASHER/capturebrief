# CaptureBrief product-engine / fulfillment red team — 2026-09-21

Scope: controlled repository fixtures and temporary artifacts only. No customer
records, external messages, payments, protected portals, or live bid decisions
were used.

Baseline: `main@0f0136e1be8b01c6513f9b134af3349265abd895`.

## Method

The red team added adversarial regression cases first and required them to fail
against the baseline behavior before code was changed. The attacks focused on
cases where a structurally plausible record could be mistaken for verified
evidence, clean watch status, or attributable customer outcome evidence.

The first attack wave reproduced six fail-open cases. The expanded wave
reproduced twelve. Subsequent watch and provenance attacks brought the confirmed
total to seventeen.

## Confirmed fail-open cases

### Decision Evidence

1. A resolved `SUPPORTED` finding could be complete with zero exact cited passages.
2. A `SUPPORTED` finding could rely only on a `CONTEXT` citation.
3. Evidence observed after the declared decision time could support that earlier decision.
4. Snapshot URL/observation metadata could diverge from its bound source record.
5. A human review performed after the declared decision time could support the earlier decision.
6. A resolved finding could retain `rule_scope = UNRESOLVED`.
7. A resolved finding could depend on `rule_links.applicability = UNRESOLVED`.
8. Resolved rule applicability could omit an exact pursuit-specific basis passage.
9. A rule-version object could label solicitation text as FAR/DFARS-style rule text.
10. An `AMENDS`/`SUPERSEDES`/`CORRECTS` relation could exist without an exact retained passage establishing the relationship.

### Targeted 14-day watch

11. `watch-check` could produce `requires_human_review=true` while returning process exit code 0.
12. Reusing an unchanged stale local case on a later day could appear to show no change without proving a fresh observation.
13. Currentness could degrade/expire while the underlying action identifiers remained the same without an explicit currentness-verdict event.
14. The advertised 14-day watch had no hash-bound end timestamp and could be evaluated beyond day 14 without an explicit expiration state.

### Commercial outcome attribution

15. One case ID could combine events carrying different case-content fingerprints.
16. Buyer feedback/action-effect evidence could count without a matching delivered bundle.
17. A repeat request could count without a matching delivered bundle.

The remediation also applies the same delivery binding to retractions so
post-delivery correction evidence cannot float independently of the delivered artifact.

## Remediation

Decision Evidence now requires semantically appropriate exact passages for
resolved findings, prevents temporal look-ahead, binds snapshot source metadata,
keeps unresolved rule authority from hiding behind resolved buyer language,
checks the source kind behind a rule identity, and requires exact authority
evidence for a source-version relationship.

The watch now has an observation watermark and exact 14-day `watch_until`.
No-change status requires evidence that the retained public observation advanced
since baseline (except deterministic same-instant replay). Verdict degradation
is explicit. An expired watch is explicit. Review-required observations return
exit code 3 so unattended automation cannot treat them as successful no-change
runs.

The outcome summary now requires one case fingerprint per case ID and only
counts feedback/repeat/retraction evidence that can be bound to a matching
delivery-bundle SHA at or before the downstream event.

## Evidence

Failing attack runs were retained in GitHub Actions history before the fixes.
Notable runs:

- `35672827084`: initial six fail-open cases reproduced.
- `35672952245`: expanded twelve-case truth-layer attack reproduced.
- `35673378148`: three additional watch-lifecycle weaknesses reproduced.
- `35673589198`: fake rule identity and unsupported version-relation attacks reproduced.

The patched branch later passed the full Product Core workflow with all
adversarial cases retained.

## Boundaries

A passing software red team is not:

- proof that a real buyer's source packet is correct;
- legal/procurement advice;
- proof that public publisher data is authentic beyond the retained source evidence;
- proof of customer value or willingness to pay;
- permission to send a bundle or any message;
- authorization to change bid posture automatically.

Every external email/message still requires the owner's approval of that
specific message. A completed delivery artifact does not supply that approval.
